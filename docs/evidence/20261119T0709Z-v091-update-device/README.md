# V0.9.1：实机 0.9.1-rc.2 → 0.9.1 更新（验证停机超时的修复）

生产设备，用户在网页上一键更新后在 root shell 里执行检查命令并贴回（`01-after-update-rc2-to-091.txt`）。

| 时间（+08:00） | 事件 |
| --- | --- |
| 15:08:13 | 下载并验签完成，写入请求 |
| 15:09:06.80 | 定时任务接手，主服务开始停止 |
| 15:09:06 | 主服务已停止（同一秒内） |
| 15:09:12 | 0.9.1 启动（commit `8e33db9`） |
| 15:09:15 | root 侧健康检查通过，写结果，`ok: true` |
| 15:09:17 | `updated from 0.9.1-rc.2 to 0.9.1` |

## 结论

- **停机超时的修复有效**：这次停的是带修复的 rc.2 进程，`service stopping` 到 `Stopped` 在同一秒内完成；没有 `context deadline exceeded`，也没有 `Failed with result 'exit-code'`。
- 与前两次更新对比：

  | 更新 | 停主服务耗时 | 主服务不可用 | root 侧全程 |
  | --- | --- | --- | --- |
  | 0.9.0 → rc.1 | 10 秒（超时，退出码 1） | 16 秒 | 19 秒 |
  | rc.1 → rc.2 | 10 秒（超时，退出码 1） | 16 秒 | 19 秒 |
  | rc.2 → 0.9.1 | 不到 1 秒 | 6 秒 | 9 秒 |

- 「更新完成」在结果写入 2 秒后报告，与上次一致。
- 至此第二阶段在架构文档 §19.6.9 里列出的「仍未验证」项只剩回滚（用户决定不做实机演练）。

## 预期内的现象

- 15:09:12 新进程先报告了一条 `update.failed`（`stage` / `too many levels of symbolic links`），是测试方案 N4 留在结果文件里的旧结果，不是这次更新的失败。

## 小瑕疵（未修）

- 那条旧结果的英文消息是 `update to  failed at stage`，中间多一个空格：N4 在取到版本号之前就被拒，结果里 `to` 为空，消息模板没有处理这种情况。只影响日志与事件原文的措辞；前端中文文案在 `to` 为空时会省略版本号，不受影响。
